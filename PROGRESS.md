## Notas de compatibilidad de librerias

- Next.js 16: `middleware.ts` fue renombrado a `proxy.ts` (confirmado en la documentacion del proyecto vercel:nextjs).
- AI SDK v7 (`ai@7.0.105`): los tools usan `inputSchema` (ya no `parameters`). Se usa `streamText` + `tool()` + `stopWhen: isStepCount(5)` en vez del `maxSteps` de versiones anteriores. Se usa `createUIMessageStream`/`createUIMessageStreamResponse` para el endpoint `/api/chat`.
- Tipografia: "Atkinson Hyperlegible Next" no esta disponible aun en `next/font/google`; se usa "Atkinson Hyperlegible" (pesos 400/700) como indica el spec como alternativa.
- `@types/node` se fijo en `^24` (en vez de `^20` del scaffold por defecto) porque `vitest@5` requiere `@types/node >=22`.
- `util.promisify(crypto.scrypt)` no tipa bien la sobrecarga con `options`; se cambio a `crypto.scryptSync` en `lib/auth.ts` (mismo resultado, sin el problema de tipos).
- Bug conocido de npm con dependencias opcionales (rolldown/vitest) causo `Cannot find native binding`; se resolvio borrando `node_modules`/`package-lock.json` y reinstalando.
- Seed genero 74 sintomas (el spec sugiere "~80"); es una aproximacion razonable, todas las 15 especialidades quedan cubiertas.
- **Importante**: el spec sugiere el formato `scrypt$N$r$p$sal$hash` para `ADMIN_PASSWORD_HASH`. El loader de env de Next.js (`@next/env`, usa `dotenv-expand`) interpola `$nombre` dentro de archivos `.env*` locales (`next dev`/`next build`), lo que corrompia el hash porque `$16384`, `$8`, `$1` y el salt en base64 se interpretaban como referencias a variables inexistentes y se reemplazaban por cadena vacia. Esto NO afecta produccion en Vercel (las variables llegan directo a `process.env`, no se leen desde archivo), pero rompe el login en desarrollo local. Se cambio el formato a `scrypt:N:r:p:sal:hash` con base64url (sin `$`) para eliminar el problema de raiz.
- `proxy.ts`: el `matcher` de `proxyConfig` no excluyo `/login` de forma confiable en `next dev` (Turbopack), causando un bucle de redireccion. Se agrego una lista `PUBLICO` verificada dentro de la propia funcion `proxy()` como defensa adicional, sin depender solo del matcher.
- **Bug critico corregido en produccion (post fase 11)**: el export `proxyConfig` documentado para Next.js 16 nunca tuvo efecto en la version instalada (16.3.5). El analizador de Next.js sigue leyendo el matcher desde un export llamado `config` (`extractExportedConstValue(ast, 'config')` en `next/dist/build/analysis/get-page-static-info.js`), aunque el archivo/funcion se llamen `proxy.ts`/`proxy()`. Como `proxyConfig` se ignoraba en silencio (sin error ni warning), el proxy corria sobre **todas** las rutas, incluido `/_next/static/*`, que quedaba redirigido (307) a `/login` (HTML) en vez de servir JS -> el navegador fallaba con "Unexpected token '<'" al intentar ejecutar HTML como JS. Se corrigio renombrando el export a `config` (verificado que el matcher ahora aparece en `.next/server/functions-config-manifest.json` bajo `/_middleware`) y se redeployo. Esto invalida la guia de la skill `vercel:nextjs` sobre el nombre `proxyConfig` para esta version de Next.js; para futuras versiones, verificar contra el codigo fuente instalado, no solo la documentacion.
- `convertToModelMessages` en `ai@7` es asincrono (`Promise<ModelMessage[]>`); se agrego `await` en `app/api/chat/route.ts`.
- `MODEL_AGENTE` configurado (`gpt-5-nano`) es un modelo de razonamiento: gasta tokens de salida en razonamiento interno antes del texto visible. Se uso `providerOptions.openai.reasoningEffort: "low"` y `maxOutputTokens: 700` (mas alto que un modelo no razonador) para evitar respuestas vacias por agotar el presupuesto en razonamiento.
- El endpoint `/api/chat` no hace streaming token a token del texto final: los pasos de herramientas se transmiten en vivo, pero el texto de cierre se espera completo (`await resultado.text`) para poder aplicar la guarda de montos antes de enviarlo. Es una decision deliberada: la guarda no puede editar texto ya enviado al cliente.
- `mcp-handler` 2.x requiere `@modelcontextprotocol/server` (no `@modelcontextprotocol/sdk`, que es la libreria de la generacion anterior). El README del paquete lo indica explicitamente; se instalo el paquete correcto tras un primer intento fallido.
- Cada `npm install` de un paquete nuevo volvio a disparar el bug conocido de npm con dependencias opcionales (`Cannot find native binding` en `rolldown`, usado por Vitest). Se resolvio repetidamente borrando `node_modules` y `package-lock.json` y reinstalando; si el agente vuelve a instalar dependencias en el futuro, repetir el mismo remedio si aparece el mismo error.
- **Bug corregido (fase 9->10)**: `app/api/auth/login/route.ts` llamaba a `verificarLimite` (que incrementa el contador en toda llamada) antes de validar la contraseña, asi que los logins CORRECTOS tambien contaban para el bloqueo de fuerza bruta. Esto rompio el smoke test tras correrlo varias veces seguidas en produccion (qued o bloqueado con E429). El spec pide bloquear solo tras "5 fallos", no 5 intentos totales. Se agregaron `estaBloqueado` / `registrarFallo` / `limpiarLimite` en `lib/limites.ts`: la ruta ahora solo registra fallo en credenciales invalidas y limpia el contador en un login exitoso. `verificarLimite` (incrementa siempre) se mantiene para la cuota de `/api/chat`, donde si corresponde contar cada consulta.
